PENGEMBANGAN APLIKASI SHUTTLE SYSTEM  
Deskripsi Sistem 
Aplikasi ini bertujuan dari untuk menyediakan layanan yang dapat digunakan oleh customer, 
driver, dan admin. Sistem ini dirancang agar mampu mengelola jadwal perjalanan shuttle, 
mengatur pemesanan kursi, serta mengontrol kapasitas kendaraan. Selain itu, sistem juga dapat 
menampilkan posisi shuttle secara real-time dan menunjukkan rute perjalanan yang ditempuh. 
Tidak hanya itu, sistem ini juga mampu menyimpan histori perjalanan serta berjalan secara 
terintegrasi antara aplikasi mobile, backend, dan web dashboard. 
Model Proses yang Digunakan 
Model yang digunakan adalah Scrum, karena project ini memungkinkan adanya perubahan 
fitur selama proses pengembangan dan dikerjakan secara bertahap. karena tim bisa fokus 
selama sprint berjalan sesuai dengan daftar kebutuhan yang ingin dibuat pada backlog. 
Tahapan Pengembangan Sistem (SDLC) 
1.     Product Backlog 
Pada tahap ini, tim menyusun daftar seluruh kebutuhan sistem berdasarkan fitur yang akan 
dikembangkan. Contoh backlog pada sistem shuttle: 
● Login pengguna (customer, driver, admin) 
● Melihat jadwal shuttle 
● Booking kursi 
● Pemilihan kursi 
● Tracking posisi shuttle 
● Manajemen jadwal (admin) 
● Monitoring perjalanan 
● Histori perjalanan 
2.     Sprint Planning 


Tim memilih beberapa fitur dari backlog untuk dikerjakan dalam satu sprint (biasanya 1–2 
minggu). 
Contoh Sprint 1: 
● Sistem login 
● Melihat jadwal shuttle 
● Tampilan dashboard 
Contoh Sprint 2: 
● Booking kursi 
● Pemilihan kursi 
● Manajemen kapasitas kendaraan 
3.     Development 
Tim mulai mengembangkan sistem sesuai fitur yang dipilih pada sprint. 
● Pada project ini menggunakan: 
● Android Studio untuk mobile app 
● Laravel untuk backend 
● MySQL untuk database 
Setiap fitur dikembangkan secara bertahap dan terintegrasi antara mobile, backend, dan 
database. 
4.     Daily Meeting 
Setiap hari tim melakukan pertemuan singkat untuk membahas: 
● Progress pekerjaan 
● Kendala yang dihadapi 
● Rencana pekerjaan selanjutnya 
5.     Testing dan Demo 
Setelah sprint selesai: 
● Fitur diuji (testing) untuk memastikan berjalan dengan baik 
● Sistem didemonstrasikan kepada pengguna atau dosen 
● Tim menerima feedback untuk perbaikan atau penambahan fitur

Kebutuhan Fungsional 
1. Kebutuhan Pengguna (Customer / Penumpang) 
● User dapat melakukan login ke sistem. 
● User dapat melihat jadwal shuttle berdasarkan rute dan waktu. 
● User dapat memilih rute perjalanan (asal dan tujuan). 
● User dapat melihat ketersediaan kursi secara real-time. 
● User dapat memilih kursi yang masih tersedia. 
● User dapat melakukan booking kursi. 
● User dapat melihat status booking (booked, cancelled, completed). 
● User dapat melihat posisi shuttle selama perjalanan (tracking). 
● User dapat melihat histori perjalanan. 
● User dapat mengelola profil (update data dan password). 
2. Kebutuhan Pengguna (Driver) 
● Driver dapat login ke sistem. 
● Driver dapat melihat jadwal perjalanan yang ditugaskan. 
● Driver dapat memulai perjalanan (trip). 
● Driver dapat mengupdate lokasi secara berkala (latitude & longitude). 
● Driver dapat menjalankan perjalanan hingga selesai. 
● Driver dapat menyelesaikan perjalanan (status completed). 
● Driver dapat melihat histori perjalanan.  
3. Kebutuhan Pengguna (Admin) 
● Admin dapat login ke web dashboard. 


● Admin dapat membuat jadwal shuttle (asal, tujuan, waktu, kendaraan). 
● Admin dapat mengelola kendaraan (tambah, ubah, kapasitas). 
● Admin dapat menentukan kapasitas kursi. 
● Admin dapat melihat dan memonitor booking. 
● Admin dapat memonitor perjalanan (trip monitoring). 
● Admin dapat melihat lokasi shuttle secara real-time. 
● Admin dapat melihat histori perjalanan. 
● Admin dapat melihat dashboard statistik sistem.  
4. Kebutuhan Kebutuhan (Backend / System) 
● Sistem dapat mengelola autentikasi dan otorisasi berbasis role (customer, 
driver, admin). 
● Sistem dapat mengelola jadwal shuttle. 
● Sistem dapat mengelola booking kursi. 
● Sistem dapat mengontrol kapasitas kendaraan agar tidak overbooking. 
● Sistem dapat mencegah double booking kursi. 
● Sistem dapat menyimpan dan mengelola data seat (available/booked). 
● Sistem dapat mengelola status perjalanan (scheduled, on-going, completed). 
● Sistem dapat menerima dan menyimpan lokasi driver secara berkala. 
● Sistem dapat menampilkan tracking posisi shuttle. 
● Sistem dapat menyimpan histori perjalanan dan booking. 
● Sistem dapat menyediakan API untuk mobile dan web.  
Kebutuhan Non-Fungsional 
1. Kebutuhan Kegunaan (Usability) 
● Antarmuka aplikasi harus mudah digunakan oleh user (customer, driver, 
admin). 
● Tampilan seat harus jelas membedakan kursi tersedia dan terisi. 
● Fitur tracking harus mudah dipahami oleh pengguna. 
● Navigasi menu harus sederhana dan intuitif. 
2. Kebutuhan Performa (Performance) 
● Response API harus kurang dari 3 detik. 
● Sistem harus mampu menampilkan update lokasi secara berkala (near real-
time). 
● Sistem harus tetap responsif saat banyak user melakukan booking bersamaan. 
3. Kebutuhan Keamanan (Security) 
● Password harus disimpan dalam bentuk hash. 
● Sistem harus memiliki validasi input untuk mencegah error dan serangan. 
● Sistem harus menerapkan role-based access control. 
● Data transaksi (booking) harus aman dan tidak boleh hilang. 
4. Kebutuhan Keandalan (Reliability) 
● Sistem tidak boleh crash saat digunakan atau saat demo. 
● Sistem harus memastikan tidak terjadi double booking kursi. 


● Sistem harus dapat berjalan end-to-end (booking → trip → tracking → 
selesai). 
5. Kebutuhan Skalabilitas (Scalability) 
● Sistem harus mampu dikembangkan untuk jumlah user lebih besar. 
● Backend harus mampu menangani banyak request secara bersamaan.  
6. Kebutuhan Deployment 
● Backend harus di-deploy dan dapat diakses online. 
● Web admin harus dapat diakses melalui browser. 
● Mobile app harus dapat di-build (APK/AAB). 
● Sistem harus bisa didemokan secara live end-to-end.
